# CI.md

## 目的

この文書は、各アプリでGitHub Actionsを常設し、PushやPull Requestのたびに最低限の自動品質確認を行うための共通ルールを定義する。

この文書を、**「Push」という指示にどこまで含めるか、GitHub Actionsをどう実行・確認するかの正本**とする。
ブランチ・競合・強制Push禁止などのGit操作そのものは `docs/GIT_WORKFLOW.md`、品質確認全体の順序と完成判定は `docs/QUALITY_CHECK.md` を正本とする。

最重要原則：

> 毎回のPushでは軽量CIを自動実行し、重い検査は変更内容または明示的な検査指示に応じて追加する。

毎Pushでクラッシュ / ANR、メモリ、権限 / セキュリティ、実機確認まで強制しない。
通常開発の速度を落とさず、必要なときに深く確認できる運用を基本とする。

---

## 1. 新規Androidアプリでは最初にGitHub Actionsを常設する

新しいAndroidアプリのリポジトリを作成したら、主要機能の実装より先に `.github/workflows/android-ci.yml` を配置する。

共通テンプレートは `templates/android-ci.yml` を使用し、対象アプリの構成に合わせて必要最小限だけ調整する。

Workflowをローカルに置くだけで先へ進まず、原則として最初のPushでGitHubへ反映し、Actionsが実際に有効になったことを確認してから主要機能の実装へ進む。

CIを後付けにしない。

---

## 2. 指示を3段階に分ける

品質確認は、通常作業・重点検査・フル品質ゲートの3段階に分ける。

### 2.1 「Push」「Pushして」「GitHubに反映して」

通常のPush指示では、次を1セットとして扱う。

```text
最新リモート状態を確認
↓
安全にPush
↓
軽量GitHub Actionsを実行・起動確認
↓
Actionsの完了を確認
↓
成功 / 失敗 / 未実行を確認
↓
結果をユーザーへ報告
```

毎Pushで実行する基本CIは原則として次の範囲に留める。

1. `assembleDebug`
2. `lintDebug`
3. `testDebugUnitTest`
4. `regressionCheck` が定義されている場合のみ実行
5. LintレポートArtifact保存

クラッシュ / ANR、メモリ、権限 / セキュリティ、実機確認は、通常のPushだけを理由に毎回フル実行しない。

### 2.2 「検査して」「バグチェックして」「セキュリティチェックして」

変更内容と依頼内容に応じた重点検査を追加する。

例：

- 監視・Listener・Observer変更 → メモリ、重複登録、解除、CPU負荷
- 非同期処理変更 → 競合、キャンセル、古い結果による上書き、クラッシュ / ANR
- 権限変更 → 権限拒否、取消、OS差分、不要権限
- WebView / 外部入力 / 通信変更 → セキュリティ重点確認
- DB / 保存変更 → データ移行、破損、旧データ互換性
- UI / レイアウト変更 → 回転、画面サイズ、スクロール、必要に応じて実機

変更と無関係な重い検査まで機械的に全部追加しない。

### 2.3 「全部検査して」「フルチェックして」「リリース前チェックして」

`docs/QUALITY_CHECK.md` のフル品質ゲートを実施する。

基本順序は次のとおりとし、詳細は `docs/QUALITY_CHECK.md` を正本とする。

```text
ビルド
↓
Lint
↓
テスト
↓
クラッシュ / ANR
↓
メモリ
↓
権限 / セキュリティ
↓
実機確認
```

すべて実施できない環境では、未実施項目と理由を明示する。

---

## 3. 「Push」はActions確認までを含む

ユーザーから「Push」「Pushして」「GitHubに反映して」など、GitHubへ変更を送る指示があった場合は、明示的にActions不要と指定されていない限り、Pushだけで止めず、軽量CIの完了確認と結果報告まで行う。

Actionsを回すためだけの追加確認は原則として求めない。

Push自体が成功しても、Actionsが失敗している場合は「完了」「問題なし」と扱わない。Push結果とCI結果を分けて報告する。

Workflowが自動起動しない場合は、`workflow_dispatch` が利用できるなら同じコミット・ブランチを対象に実行する。

Actionsが無効、権限不足、接続不可、Workflow不在などで実行・確認できない場合は、その事実を明示する。

---

## 4. 基本トリガー

軽量CIは原則として次で実行する。

- すべてのブランチへのPush
- Pull Request
- 必要に応じた手動実行 `workflow_dispatch`

これにより、デフォルトブランチだけでなく各Chat・各作業ブランチへPushした時点でも自動チェックを行う。

リポジトリ固有の事情で対象を絞る場合は、Push指示時に対象ブランチのCIが実際に実行されることを確認する。

---

## 5. Androidの毎Push基本タスク

GitHub Actionsでは、通常Pushの軽量ゲートとして原則次をこの順序で実行する。

1. `assembleDebug`
2. `lintDebug`
3. `testDebugUnitTest`

加えて、`regressionCheck` が定義されている場合は自動回帰確認として実行する。

`regressionCheck` はAndroid / Gradleの標準タスクではないため、存在しないアプリで無理に実行してCIを壊さない。

クラッシュ / ANR、メモリ、権限 / セキュリティ、実機確認など、CIだけで十分に確認できない項目は通常Pushへ無理に詰め込まず、重点検査またはフル品質ゲートで確認する。

---

## 6. Lintレポートを必ず保存する

`lintDebug` の結果は、GitHub ActionsのArtifactとして保存する。

Lintが失敗した場合でも原因を確認できるよう、Artifactアップロードは `if: always()` で実行する。

保存対象は、生成される範囲で次を含める。

- HTML
- XML
- TXT

例：

```text
**/build/reports/lint-results-*.html
**/build/reports/lint-results-*.xml
**/build/reports/lint-results-*.txt
```

Lintの警告件数が0でないだけで機械的に成功扱い・失敗扱いを決めず、重大度と新規増加を `docs/QUALITY_CHECK.md` に従って確認する。

Push後の結果報告では、必要に応じてLintレポートArtifactが保存されたことも確認する。

---

## 7. 重い検査は手動・重点実行へ分離する

毎Pushに向かない重い検査は、必要に応じて `workflow_dispatch`、専用Workflow、ローカル検査、エミュレータ、実機確認へ分離する。

対象例：

- Instrumented / UI testの重いセット
- 依存関係の脆弱性スキャン
- 長時間の回帰試験
- メモリリーク調査
- クラッシュ / ANR再現確認
- 複数OS / 複数端末確認
- 実機確認

毎Pushへ全部詰め込み、CIが重すぎて使われなくなる構成を避ける。

---

## 8. 失敗後も診断情報を残す

ビルド、Lint、テスト等が失敗しても、後続の診断やArtifact保存が可能な範囲で実行されるようにする。

ただし、失敗を無視してWorkflow全体を成功扱いにはしない。

CI失敗は「確認すべき異常がある」という合図として扱う。

失敗時は可能な範囲で失敗Job・Step・ログを確認し、どこで失敗したかを報告する。

---

## 9. CIとローカル確認の役割

GitHub Actionsはローカル確認の代替ではない。

通常Pushでは軽量CIを自動安全網として使い、より深い確認が必要な場合は `docs/QUALITY_CHECK.md` に従って重点検査またはフル品質ゲートを行う。

実機確認、メーカー差、権限ダイアログ、端末固有挙動などを「CIが通ったから確認済み」と扱わない。

---

## 10. CIを壊したまま放置しない

Workflowが継続的に失敗している状態を通常状態にしない。

失敗した場合は、少なくとも次を確認する。

- 今回のコード変更による失敗か
- Workflow自体の設定ミスか
- Gradle / JDK / SDK等の環境差か
- 既存から継続している失敗か
- `regressionCheck` 等の独自タスクが存在するか

テストやLintを無効化してCIを緑にするだけの修正を行わない。

---

## 11. 完成・統合時の扱い

PushまたはPull Requestを行った場合は、利用可能な範囲で軽量GitHub Actionsの完了結果まで確認する。

作業ブランチをPushした場合はそのブランチのCIを確認し、デフォルトブランチへ統合した場合は統合後のコミットに対するCIも確認する。

CIが未実行・失敗・確認不能の場合は、その事実を明示する。

CI成功だけでアプリ全体の完成判定をしない。完成判定やリリース前確認は `docs/QUALITY_CHECK.md` に従う。

---

## 最終原則

新規Androidアプリでは、

```text
リポジトリ作成
↓
共通ルール配置
↓
GitHub Actions配置
↓
GitHub Actionsを最初にPush
↓
Actionsが有効であることを確認
↓
主要機能の実装開始
```

を基本順序とする。

通常作業では、

```text
「Pushして」
↓
安全にPush
↓
軽量GitHub Actions
↓
完了結果確認
↓
結果報告
```

までを同じ依頼として扱う。

深い確認が必要な場合は、

```text
「検査して」
→ 変更内容に応じた重点検査

「全部検査して / リリース前チェックして」
→ QUALITY_CHECK.md のフル品質ゲート
```

と使い分ける。

> CIは毎回すべてを検査する仕組みではなく、日常開発を止めずに異常を早く検出し、必要なときに深い検査へ進むための安全網とする。
