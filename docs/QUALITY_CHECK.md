# QUALITY_CHECK.md

## 目的

この文書は、アプリ開発で「ビルドが通ったから完成」と判断せず、不具合・性能劣化・保守上の問題を早い段階で発見するための共通品質確認ルールを定義する。

この文書を、**品質確認の基本順序と完成判定の正本**とする。
他の共通文書では順序を重複管理せず、この文書を参照する。

最重要原則：

> `BUILD SUCCESSFUL` は「ビルドできた」という意味であり、「正常・安全・完成」を意味しない。

同時に、品質確認は「必ず何か問題を見つける作業」でもない。

> 十分に確認した結果、修正すべき問題が見つからなければ、「確認範囲では修正すべきバグは確認できない」と報告する。指摘件数を作るために問題を捻り出さない。

ただし、すべての品質確認を毎回最大規模で実行する必要はない。
通常Push、重点検査、フル品質ゲートを使い分け、変更内容に必要な深さで確認する。

---

## 0. バグ調査は根拠ベースで行う

バグチェック・監査・レビューでは、件数ではなく**実在性と影響**を重視する。

確定バグとして扱うには、少なくとも次のいずれかの根拠を求める。

- 再現できる症状
- 失敗するテスト
- ログ・例外・クラッシュ等の実行結果
- `CURRENT_SPEC.md` や明確な正常仕様との不一致
- 実際に問題へ到達することを説明できるコード経路

次は確定バグと同一視しない。

- 理論上は起こり得るが到達性を確認していないもの
- コードの好み・スタイル差
- 将来の改善案
- 性能上の可能性だけで実害を確認していないもの
- 防御的に書き換えれば安心というだけの提案

必要なら「確定バグ」「要確認候補」「改善提案」を分けて報告する。
要確認候補を、確認なしで修正しない。

### 0.1 重複監査を防ぐ

バグ調査は必ず**リモートの最新デフォルトブランチ**を基準に行う。
過去Chatのcommit、古いローカルHEAD、過去の監査結果だけを調査基準にしない。

調査開始時は原則として次の順序で確認する。

```text
最新リモートデフォルトブランチを取得
↓
調査基準HEAD / commitを確認・記録
↓
CURRENT_SPECを確認
↓
KNOWN_ISSUESを確認
↓
BUG_HISTORYを確認
↓
既出 / 修正済み / 再発 / 新規を区別
↓
調査開始
```

新規バグとして報告する前に、`docs/KNOWN_ISSUES.md` と `docs/BUG_HISTORY.md` を照合する。
`BUG_HISTORY.md` に同じ原因・同じ問題の修正済み記録がある場合は、**最新HEAD上で再発している根拠がない限り再報告しない**。

修正済み問題が最新HEADでも再現する場合は、原則として新しいBUG-IDを作らず既存BUG-IDの**再発**として扱う。
その場合は、修正済みcommit以降になぜ再発したかも確認する。

修正へ入る直前にもリモートの最新デフォルトブランチを再確認する。
調査中に別Chat・別AI・別開発者のPushでHEADが進んでいた場合は、新しいHEADへ基準を切り替え、**最新HEAD上でまだ存在する問題だけ**を修正する。

同じ領域を再監査したとき、新しい根拠がないものを別名で再度バグとして挙げない。
前回までの指摘が修正済みで、新しい問題が確認できなければ「新しいバグは確認できない」で終了してよい。

不要な変更によって正常動作を壊すことも品質劣化である。
**バグを見つけないことより、存在しないバグを作って修正することの方を避ける。**

## 1. 品質確認は3段階で使い分ける

### 1.1 通常Push

通常の「Push」「Pushして」では、`docs/CI.md` に従い軽量CIを基本とする。

原則：

```text
ビルド
↓
Lint
↓
テスト
↓
regressionCheck（毎Push向けの軽量タスクとして定義されている場合）
↓
Lintレポート保存
```

`regressionCheck` には毎Pushで無理なく実行できる軽量な回帰だけを含める。
長時間の回帰試験、重いInstrumented / UI test、実機・エミュレータ依存の確認は通常Pushへ詰め込まず、重点検査またはフル品質ゲートへ分離する。

通常Pushだけを理由に、クラッシュ / ANR、メモリ、権限 / セキュリティ、実機確認まで毎回フル実行しない。

### 1.2 重点検査

「検査して」「バグチェックして」「セキュリティチェックして」などの指示では、変更内容と依頼内容に応じて必要な検査を追加する。

変更と直接関係する危険箇所は省略しないが、無関係な重い検査まで機械的に全部実行しない。

重点検査の結果、確定バグが見つからなければ、無理に候補を増やさずそのまま報告する。

### 1.3 フル品質ゲート

「全部検査して」「フルチェックして」「リリース前チェックして」では、次の基本順序で広く確認する。

```text
ビルド
↓
Lint
↓
テスト
↓
クラッシュ / ANR
↓
メモリ
↓
権限 / セキュリティ
↓
実機確認
```

この順序は、先に機械的に検出できる問題を潰し、その後に実行時・安全性・端末固有の問題を確認するための基本ラインとする。

すべてを実行できない環境では、未実施項目と理由を明示する。

## 2. ビルド

まずコンパイル / ビルドを確認する。

ビルド成功だけでは完成ではないが、後続確認へ進む前提として、最低限ビルド可能な状態を確認する。

同時にコンパイラ警告も確認する。

特に次を優先して確認する。

- 今回の変更で新しく増えた警告
- 非推奨API
- 型・null・到達不能コード等に関する警告
- 将来のビルド失敗につながる警告
- 実行時不具合を示唆する警告

既存警告が大量にある場合も、今回の変更で悪化させない。

---

## 3. Lint / 静的解析

ビルド後にLint / 静的解析を確認する。

Lintや静的解析の警告件数が0でないだけで、直ちにアプリ全体を失敗扱いにはしない。

ただし次は放置しない。

- Error相当
- 高い重大度の警告
- 今回の変更で新しく増えた警告
- 今回変更したコードに直接関係する警告
- クラッシュ・権限・セキュリティ・互換性・性能に関係する警告

既存警告と新規警告を可能な限り区別する。

警告を減らすためだけに、必要な処理を削除したりLintを無効化したりしない。
抑制が必要な場合は理由を確認し、無意味な一括Suppressを避ける。

---

## 4. テストと回帰確認

Lint確認後に、関連する自動テストと回帰確認を行う。

変更箇所のテストだけでなく、影響を受ける関連機能も確認する。

最低限、可能な範囲で次を行う。

- 関連単体テスト
- 結合テスト / UIテスト
- 既存自動テスト
- `docs/REGRESSION_CHECKLIST.md` の関連項目
- バグ修正では必要に応じて再発防止テスト

テストを通すためにassertion削除、条件緩和、skip化などを行わない。

GitHub Actionsが常設されている場合は `docs/CI.md` に従い、Push / Pull Request後の自動結果も確認する。

---

## 5. クラッシュ / ANR

クラッシュ / ANRは、重点検査またはフル品質ゲートで必要に応じて確認する。

クラッシュ確認では正常系だけでなく、失敗しやすい経路も確認する。

例：

- null / 空データ
- 通信失敗
- 権限拒否
- 画面回転
- バックグラウンド移行・復帰
- 連続操作
- キャンセル
- アプリ再起動

クラッシュログや例外が確認できる環境では、今回の変更に関係する新しい例外がないか確認する。

ANRについては、次の処理をメインスレッドへ安易に置かない。

- 重いI/O
- 大量データ処理
- 長時間の同期処理
- 重い画像処理
- 不要な待機
- 高頻度イベントごとの重い処理

UIが固まる、タップへ反応しない、スクロールが長時間止まるなどの兆候がある場合は原因を調査する。

本番のクラッシュ / ANR監視サービスが導入されている場合は、リリース後の重大な増加も確認対象とする。

---

## 6. メモリ

メモリ確認は、監視・ライフサイクル・WebView・大きなデータ処理など、メモリ影響が疑われる変更やフル品質ゲートで重点的に行う。

次の変更では特に注意する。

- Listener / Observer / Subscription / Watcher
- `MutationObserver`
- Coroutine / Task / Timer
- Callback
- Activity / Fragment / View / Context参照
- WebView
- 大きなBitmapやキャッシュ
- 長寿命Singleton / Manager

解除可能な監視・Listener・Observerは、ライフサイクル終了時に適切に解除する。
監視処理の詳細は `docs/MONITORING.md` に従う。

ツールによるリーク検査が利用できる場合は必要に応じて使用する。
利用できない場合も、参照が残り続ける構造になっていないかコード上で確認する。

---

## 7. 権限 / セキュリティ

権限 / セキュリティ確認は、権限・Manifest・通信・WebView・外部入力・秘密情報・依存関係に関わる変更やフル品質ゲートで重点的に行う。

Androidの権限については `docs/KENGEN.md` に従い、少なくとも次を確認する。

- 必要な権限だけを要求している
- 不要な権限が残っていない
- 拒否・取消時に壊れない
- OSバージョン差を考慮している
- 端末や画面条件で使えない機能の権限を要求していない
- 特殊アクセスや端末設定が必要な場合の案内が適切

セキュリティでは、変更内容に応じて少なくとも次を確認する。

- APIキー、トークン、パスワード、秘密鍵等の秘密情報をリポジトリやアプリ内へ不用意に埋め込んでいない
- ログ、クラッシュログ、デバッグ出力へ個人情報・認証情報・機密データを不要に出していない
- Activity / Service / Receiver / Provider等を不要にexportしていない
- Intent、Deep Link、外部入力を無条件に信頼せず、必要な検証をしている
- WebViewを使う場合、不要なJavaScript Interface、危険なURL遷移、過剰な設定を有効にしていない
- 平文HTTP等の安全性の低い通信を理由なく許可していない
- 機密データを不要に外部ストレージや平文で保存していない
- Debug用設定・テスト用エンドポイント・一時的な認証回避を本番向け設定へ残していない

依存関係については、可能な範囲で次を確認する。

- 既知の脆弱性
- サポート終了・長期間更新されていない依存
- 不要になった依存
- 同じ用途の重複依存
- 依存追加による権限やManifest変更
- targetSdk / compileSdk等との互換性

脆弱性チェック用の仕組みやツールが存在する場合は使用し、重大な既知脆弱性を理由なく放置しない。

---

## 8. 実機確認

実機確認は、UI、回転、ライフサイクル、権限、バックグラウンド、通知、ストレージ、ハードウェア、WebView、端末差など実機依存性がある変更やフル品質ゲートで重視する。

実機を用意できない場合はエミュレータで代替できる範囲を確認し、実機未確認であることを明示する。

特に次の変更では実機確認を重視する。

- UI変更
- 画面サイズ・画面回転対応
- ライフサイクル
- 権限
- バックグラウンド処理
- 通知
- ストレージ / ファイル
- カメラ / マイク / Bluetooth / 位置情報
- WebViewや外部サービス連携
- 端末・OSバージョン差がある機能
- メーカー差が影響する機能

ビルド、Lint、テスト、エミュレータ確認だけで実機確認済みと扱わない。

---

## 9. 変更内容に応じて重点検査する

基本順序を参考にしつつ、変更内容から危険箇所を判断して重点検査を追加する。

例：

- UI / レイアウト変更 → 画面サイズ、回転、スクロール、実機
- 非同期処理変更 → 競合、キャンセル、古い結果の上書き、クラッシュ / ANR
- 監視処理変更 → `docs/MONITORING.md`、重複登録、解除、メモリリーク、CPU負荷
- DB / 保存変更 → データ移行、破損、旧データ互換性
- 権限変更 → `docs/KENGEN.md` の回帰確認
- WebView / 通信 / 外部入力変更 → セキュリティ重点確認
- 依存変更 → 脆弱性・互換性確認
- バージョン更新 → `docs/VERSIONING.md` の確認

高負荷な検査を毎回最大規模で実施する必要はないが、変更内容に直接関係する危険箇所は省略しない。

問題候補を見つけた場合も、修正前に `## 0. バグ調査は根拠ベースで行う` の基準で確定バグかどうかを確認する。

---

## 10. リリース前はフル品質ゲートを基本とする

配布APK / AABなど正式版を作る前は、通常作業より広い範囲で品質確認する。

品質ゲートの順序は `## 1. 品質確認は3段階で使い分ける` のフル品質ゲートと同じとし、ここで別の順序を定義しない。

加えて、バージョン情報、README、CURRENT_SPEC、回帰項目など配布に関係する文書・設定も確認する。

---

## 11. 未確認を隠さない・問題を捏造しない

実機がない、対象OSを用意できない、外部サービスへ接続できないなどの理由で確認できない項目がある場合は、その事実を明示する。

次を禁止する。

- 実行していないテストを「問題なし」と言う
- 実機未確認なのに「実機確認済み」と言う
- Lint警告が残っているのに「警告0」と言う
- クラッシュ / ANR / メモリリーク未確認なのに「問題なし」と断定する
- 権限 / セキュリティ未確認なのに安全確認済みと断定する
- CIが失敗・未実行なのに「自動チェック済み」と断定する
- 根拠がないのに「バグあり」と断定する
- バグが見つからないという理由だけで、改善案や仮説を確定バグへ格上げする
- 修正済みバグを、最新HEADでの再発確認なしに新規バグとして再報告する

確認済み・未確認・失敗を分けて報告する。
バグ調査では、確定バグ・要確認候補・改善提案も必要に応じて分ける。

---

## 完成判定

アプリ開発の完成判定は、単一の検査結果ではなく、変更内容とリリース段階に必要な複数の品質ゲートで判断する。

通常Pushの軽量CI成功だけで「アプリ全体が完成・安全」と断定しない。
リリース前やフルチェック指示では、`## 1. 品質確認は3段階で使い分ける` のフル品質ゲートを使用する。

> 「ビルドが通った」ではなく、「その変更と配布段階に必要な品質確認を通過し、未確認事項も明示できた」状態を完成とする。
