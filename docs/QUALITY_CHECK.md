# QUALITY_CHECK.md

## 目的

この文書は、アプリ開発で「ビルドが通ったから完成」と判断せず、不具合・性能劣化・保守上の問題を早い段階で発見するための共通品質確認ルールを定義する。

最重要原則：

> `BUILD SUCCESSFUL` は「ビルドできた」という意味であり、「正常・安全・完成」を意味しない。

コード変更後は、変更内容に応じた品質確認を行い、確認できなかった項目を確認済みとして扱わない。

---

## 1. 毎回の基本完了ライン

コード変更を伴う作業では、可能な範囲で最低限次を確認する。

1. コンパイル / ビルド
2. コンパイラ警告の確認
3. Lint / 静的解析
4. 関連する自動テスト
5. `docs/REGRESSION_CHECKLIST.md` に基づく回帰確認
6. 実機またはエミュレータでの主要動作確認
7. クラッシュ・ANRの兆候確認
8. メモリリークの可能性確認
9. 依存関係の既知脆弱性・問題の確認
10. 最終差分確認

すべてを実行できない環境では、未実施項目と理由を明示する。

---

## 2. ビルド成功だけで完成としない

ビルド成功は重要だが、それだけでは次を保証しない。

- 実行時クラッシュがない
- UIが正しく動く
- 権限拒否時にも動く
- 回帰不具合がない
- ANRがない
- メモリリークがない
- 性能劣化がない
- 依存関係に既知の問題がない

そのため、ビルド成功後に残りの品質確認を続ける。

---

## 3. コンパイラ警告を確認する

コンパイラ警告を「ビルドが通ったから問題ない」と無視しない。

特に次を優先して確認する。

- 今回の変更で新しく増えた警告
- 非推奨API
- 型・null・到達不能コード等に関する警告
- 将来のビルド失敗につながる警告
- 実行時不具合を示唆する警告

既存警告が大量にある場合も、今回の変更で悪化させない。

---

## 4. Lint / 静的解析

Lintや静的解析の警告件数が0でないだけで、直ちにアプリ全体を失敗扱いにはしない。

ただし次は放置しない。

- Error相当
- 高い重大度の警告
- 今回の変更で新しく増えた警告
- 今回変更したコードに直接関係する警告
- クラッシュ・権限・セキュリティ・互換性・性能に関係する警告

既存警告と新規警告を可能な限り区別する。

警告を減らすためだけに、必要な処理を削除したりLintを無効化したりしない。
抑制が必要な場合は理由を確認し、無意味な一括Suppressを避ける。

---

## 5. テストと回帰確認

変更箇所のテストだけでなく、影響を受ける関連機能も確認する。

最低限、可能な範囲で次を行う。

- 関連単体テスト
- 結合テスト / UIテスト
- 既存自動テスト
- `docs/REGRESSION_CHECKLIST.md` の関連項目
- バグ修正では必要に応じて再発防止テスト

テストを通すためにassertion削除、条件緩和、skip化などを行わない。

---

## 6. 実機・エミュレータ確認

アプリ動作に影響する変更では、可能な限り実機またはエミュレータで確認する。

特に次の変更では実行確認を重視する。

- UI変更
- 画面サイズ・画面回転対応
- ライフサイクル
- 権限
- バックグラウンド処理
- 通知
- ストレージ / ファイル
- カメラ / マイク / Bluetooth / 位置情報
- WebViewや外部サービス連携
- 端末・OSバージョン差がある機能

ビルドと静的解析だけで実機確認済みと扱わない。

---

## 7. クラッシュ確認

変更後は、対象機能の正常系だけでなく、失敗しやすい経路も確認する。

例：

- null / 空データ
- 通信失敗
- 権限拒否
- 画面回転
- バックグラウンド移行・復帰
- 連続操作
- キャンセル
- アプリ再起動

クラッシュログや例外が確認できる環境では、今回の変更に関係する新しい例外がないか確認する。

本番のクラッシュ監視サービスが導入されている場合は、リリース後の重大なクラッシュ増加も確認対象とする。

---

## 8. ANR・メインスレッド負荷

ANRはクラッシュとは別に確認する。

次の処理をメインスレッドへ安易に置かない。

- 重いI/O
- 大量データ処理
- 長時間の同期処理
- 重い画像処理
- 不要な待機
- 高頻度イベントごとの重い処理

UIが固まる、タップへ反応しない、スクロールが長時間止まるなどの兆候がある場合は原因を調査する。

バックグラウンドへ移すだけで競合や不要な並列処理を増やさない。

---

## 9. メモリリーク確認

次の変更ではメモリリークの可能性を特に確認する。

- Listener / Observer / Subscription / Watcher
- `MutationObserver`
- Coroutine / Task / Timer
- Callback
- Activity / Fragment / View / Context参照
- WebView
- 大きなBitmapやキャッシュ
- 長寿命Singleton / Manager

解除可能な監視・Listener・Observerは、ライフサイクル終了時に適切に解除する。

ツールによるリーク検査が利用できる場合は必要に応じて使用する。
利用できない場合も、参照が残り続ける構造になっていないかコード上で確認する。

---

## 10. 依存関係の安全性

依存関係は「ビルドできるから安全」と判断しない。

可能な範囲で次を確認する。

- 既知の脆弱性
- サポート終了・長期間更新されていない依存
- 不要になった依存
- 同じ用途の重複依存
- 依存追加による権限やManifest変更
- targetSdk / compileSdk等との互換性

依存を追加・更新した場合は特に重点的に確認する。

脆弱性チェック用の仕組みやツールが存在する場合は使用し、重大な既知脆弱性を理由なく放置しない。

---

## 11. 変更内容に応じて重点検査する

毎回すべての高負荷検査を機械的に最大規模で行うのではなく、変更内容から危険箇所を判断して重点検査を追加する。

例：

- UI / レイアウト変更 → 実機、画面サイズ、回転、スクロール
- 非同期処理変更 → 競合、キャンセル、古い結果の上書き
- 監視処理変更 → 重複登録、解除、メモリリーク、CPU負荷
- DB / 保存変更 → データ移行、破損、旧データ互換性
- 権限変更 → `docs/KENGEN.md` の回帰確認
- 依存変更 → 脆弱性・互換性確認
- バージョン更新 → `docs/VERSIONING.md` の確認

---

## 12. リリース前は広めに確認する

配布APK / AABなど正式版を作る前は、通常作業より広い範囲で品質確認する。

最低限、可能な範囲で次を確認する。

- Release相当ビルド
- Lint / 静的解析
- 自動テスト
- 回帰チェック
- 主要画面・主要機能の実機確認
- 権限の許可・拒否
- クラッシュの有無
- ANRの兆候
- メモリリークの兆候
- 依存関係の既知脆弱性
- バージョン情報
- README / CURRENT_SPEC等の文書

---

## 13. 未確認を隠さない

実機がない、対象OSを用意できない、外部サービスへ接続できないなどの理由で確認できない項目がある場合は、その事実を明示する。

次を禁止する。

- 実行していないテストを「問題なし」と言う
- 実機未確認なのに「実機確認済み」と言う
- Lint警告が残っているのに「警告0」と言う
- クラッシュ / ANR / メモリリーク未確認なのに「問題なし」と断定する

確認済み・未確認・失敗を分けて報告する。

---

## 完成判定

アプリ開発の完成判定は、単一の検査結果ではなく複数の品質ゲートで判断する。

基本の流れ：

```text
ビルド
↓
コンパイラ警告確認
↓
Lint / 静的解析
↓
テスト・回帰確認
↓
実機 / エミュレータ確認
↓
クラッシュ・ANR・メモリリーク確認
↓
依存関係の安全性確認
↓
最終差分確認
```

> 「ビルドが通った」ではなく、「必要な品質確認を通過し、未確認事項も明示できた」状態を完成とする。
