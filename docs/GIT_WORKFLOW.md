# GIT_WORKFLOW.md

## 目的

この文書は、複数Chat・複数AI・複数開発者が同じリポジトリを並行して変更するときに、互いの更新を消さず安全にGitHubへ反映するための共通ルールを定義する。

最重要原則：

> 他の作業を上書きしない。各作業を分離し、最新状態を取り込んでから通常Pushする。

この文書で「デフォルトブランチ」とは、そのリポジトリで現在設定されている `main`、`master` 等の基準ブランチを指す。ブランチ名を推測で固定しない。

---

## 1. 各Chat・各作業ごとにブランチを分ける

並行作業がある場合は、原則としてChatまたは独立した作業単位ごとに専用ブランチを作る。

例：

```text
<default-branch>
├─ bugfix/download-badge-chat1
├─ bugfix/player-chat2
└─ feature/settings-chat3
```

同じ作業ブランチを複数Chatで同時に編集しない。

ブランチ名は、何の作業か分かる名前にする。Chat番号や短い識別子を付けてもよい。

---

## 2. ブランチは最新のデフォルトブランチから作る

作業開始前にリモートの最新状態を取得し、最新のデフォルトブランチを基点に作業ブランチを作る。

古いローカル状態からそのまま作業を始めない。

作業開始時に最低限確認するもの：

- リモートのデフォルトブランチの最新状態
- 現在のHEAD
- 未コミット差分
- 対象ファイルの最新内容
- 他Chat・他AIが触っている可能性のある関連ファイル

---

## 3. 並行作業中はデフォルトブランチへ直接Pushしない

複数Chatや複数作業が同時進行している場合は、原則として各作業ブランチへPushする。

デフォルトブランチへ直接書き込むことで他作業の更新順序を乱さない。

並行作業が存在しない小さな単独作業では直接更新してもよいが、Push前の最新確認と競合防止ルールは同じように守る。

---

## 4. Push直前に必ず最新状態を確認する

作業開始時だけでなく、Pushまたはマージ直前にもリモートの最新状態を再取得する。

自分の作業開始後にデフォルトブランチが更新されていた場合は、その変更を自分の作業ブランチへ取り込んでからPush・マージする。

ユーザーから「Push」「Pushして」等の指示があった場合は、GitHub Actionsが常設されているリポジトリでは `docs/CI.md` に従い、Pushだけで終了せず、そのPushに対応するActionsの起動・完了・成否確認までを同じ依頼として扱う。Actionsを回すためだけの追加確認は原則として求めない。

基本手順：

```text
作業開始
↓
最新のリモートデフォルトブランチを確認
↓
専用ブランチで変更
↓
テスト・回帰確認
↓
Push直前にリモートデフォルトブランチを再取得
↓
他の更新があれば自分のブランチへ取り込む
↓
競合・論理競合を確認
↓
再テスト・最終差分確認
↓
通常Push
↓
GitHub Actionsを実行・完了確認
↓
CI結果を確認
↓
安全を確認してデフォルトブランチへ統合
```

CIが失敗した場合は、Push自体が成功していても「問題なし」「完了」と扱わず、失敗箇所を確認して報告する。

---

## 5. 通常Pushを使い、強制Pushしない

通常開発では次を禁止する。

- `git push --force`
- `git push -f`
- 他作業を上書きする目的の `--force-with-lease`
- non-fast-forward拒否を無理に突破する操作

Pushがnon-fast-forwardで拒否された場合は、エラーを安全装置として扱う。

強制的に送らず、リモートの最新変更を取得し、内容を確認して自分のブランチへ統合してから再度通常Pushする。

履歴修復などで強制Pushが本当に必要な場合は、影響範囲を確認し、ユーザーから明示的な許可を得た場合だけ行う。

---

## 6. 公開済み作業ブランチでは履歴を書き換えない

他のChat・AI・開発者が参照する可能性がある公開済みブランチでは、通常はrebaseによる履歴書き換えを避ける。

最新のデフォルトブランチを取り込む必要がある場合は、他作業を消さない方法で統合する。

履歴をきれいにすることより、並行作業を失わないことを優先する。

---

## 7. コンフリクトは双方の変更を理解して解決する

コンフリクトが発生した場合、自分側または相手側を機械的に全面採用しない。

確認すること：

- 自分の変更目的
- 相手の変更目的
- 両方を残せるか
- 重複処理にならないか
- 片方の修正で片方のバグが再発しないか
- CURRENT_SPECやテストと矛盾しないか

競合解決後は、関連テストと回帰確認をもう一度行う。

判断できない競合は勝手に解消せず、内容を報告して確認する。

---

## 8. コンフリクトが出なくても安全とは限らない

Git上のコンフリクトがない場合でも、論理的な競合が起こることがある。

例：

- 別ファイルから同じ状態を書き換えている
- 一方が旧関数を削除し、もう一方がその関数を利用している
- 同じイベントに別々のListenerを追加している
- 同じバグを異なる方法で二重修正している
- UI変更と内部仕様変更が食い違っている

統合前に、変更ファイルだけでなく関連する呼び出し元・呼び出し先・状態管理も必要に応じて確認する。

---

## 9. 他Chatの変更を消さない

他Chat・他AI・他開発者が作った変更を、古い内容で上書きしない。

特に次を禁止する。

- 古いファイル全文をそのまま書き戻す
- 他作業のコミットを理由なくrevertする
- 競合時に自分側だけを全面採用する
- 自分の修正と無関係な差分を削除する
- 他人の未確認変更を「不要そう」という理由だけで消す

作業対象外の変更を見つけた場合は保持する。

---

## 10. 共有ファイルは特に慎重に扱う

次のような複数作業から触られやすいファイルは、更新直前に必ず最新内容を再取得する。

- `AGENTS.md`
- `README.md`
- `docs/CURRENT_SPEC.md`
- `docs/REGRESSION_CHECKLIST.md`
- `docs/KNOWN_ISSUES.md`
- `docs/BUG_HISTORY.md`
- Gradle設定
- Manifest
- 共通状態管理
- 共通UI・テーマ

共有ファイルを全文置換する必要がある場合は、最新内容を基に編集し、既存の他作業の追記を保持する。

---

## 11. GitHub API・AIツールから更新する場合

GitHub APIやAIのファイル更新機能を使う場合も、通常のGitと同じ安全原則を適用する。

更新前に対象ファイルの最新内容とSHAを取得する。

古いSHAによる更新が拒否された場合は、最新ファイルを再取得し、他作業の変更を保持したうえで自分の変更を統合する。

競合を避けるために、エラーを無視して古い全文を再送しない。

---

## 12. 破壊的なGit操作を避ける

並行作業中は、他作業の未コミット変更や履歴を消す可能性がある操作を安易に行わない。

特に注意するもの：

- `git reset --hard`
- `git clean -fd`
- ファイル全体を古い版へ戻す操作
- 無確認の大量revert
- 強制Push

必要な場合は、対象と影響を確認してから行う。

---

## 13. デフォルトブランチへ統合する前に確認する

作業ブランチをデフォルトブランチへ統合する前に、最低限次を確認する。

- 最新のデフォルトブランチの変更を取り込んでいる
- コンフリクトを解消している
- 論理競合を確認している
- 関連テストを実行している
- 回帰確認を行っている
- GitHub Actionsが常設されている場合は、作業ブランチのPushに対するCI結果を確認している
- CURRENT_SPEC・README・その他文書が必要に応じて更新されている
- 最終差分に他作業の削除が含まれていない

確認できない項目がある場合は明示する。

---

## 14. 統合後

デフォルトブランチへの統合後は、GitHub Actionsが常設されている場合、統合後コミットに対するCIの完了結果も確認する。

その後、必要に応じて不要になった作業ブランチを削除する。

ただし未統合のコミットが残っていないことを確認してから削除する。

別Chatがまだ使用しているブランチを勝手に削除しない。

---

## 最終原則

並行開発では、速くPushすることよりも、他の変更を失わないことを優先する。

> Chatごとに作業を分離し、Push直前にデフォルトブランチの最新状態を取り込み、強制上書きせず通常Pushする。Pushを指示された場合はActionsの結果確認まで行う。

GitがPushを拒否した場合は、強制突破するのではなく「他の更新が存在する」という合図として扱う。
